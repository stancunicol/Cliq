\chapter{Despre acest manual}

\section{Scop}

\Cliq{} este un instrument local pentru pregătirea testelor de interfață web. Aplicația scanează o pagină încărcată în browser, salvează elementele cu care se poate interacționa, permite alcătuirea unui scenariu pas cu pas și generează clase Page Object Selenium în C\#, împreună cu teste NUnit.

Manualul urmărește utilizarea reală a produsului, de la alegerea unui workspace până la întreținerea codului generat. Sunt prezentate separat cele două interfețe:

\begin{itemize}
  \item \textbf{Cliq Desktop}, folosit pentru navigare, scanare, editarea rapidă a fluxurilor, rulare și generare;
  \item \textbf{Cliq for Visual Studio}, extensia care adaugă editare completă, setări, secrete, review de rescanare și administrarea metodelor C\# personalizate.
\end{itemize}

Cele două interfețe folosesc același format de workspace. O pagină sau un test salvat dintr-o interfață poate fi deschis din cealaltă.

\section{Motivație și obiective}

Scrierea manuală a testelor de interfață presupune, de obicei, aceleași etape repetitive pentru fiecare pagină nouă: găsirea unor locatori stabili, scrierea clasei Page Object corespunzătoare și menținerea ei sincronizată cu orice schimbare ulterioară a paginii. \Cliq{} automatizează partea mecanică a acestui proces, descoperirea elementelor și generarea codului, dar păstrează sub controlul utilizatorului deciziile care contează: ce locator se folosește, ce se întâmplă cu o metodă scrisă manual, ce schimbare se aplică la o rescanare.

Obiectivul proiectului este un flux complet, de la o pagină web până la un test NUnit funcțional, fără ca vreo etapă din mijloc să fie ghicită sau corectată tacit de aplicație.

\section{Principiul de funcționare}

Descoperirea și generarea sunt bazate pe reguli. Cliq nu trimite pagina ori datele workspace-ului către un serviciu de inteligență artificială. Scanarea folosește Puppeteer, iar rularea testelor folosește Selenium WebDriver.

Browserul inclus în Desktop servește navigării manuale și alegerii paginii. Testul este executat într-o fereastră separată și vizibilă, cu același tip de motor folosit de testul NUnit generat.

\important{Folosiți medii și conturi de test. Un scenariu poate trimite formulare sau poate modifica datele aplicației testate.}

\chapter{Arhitectura Cliq}

\section{Prezentare generală}

\Cliq{} este format dintr-un backend .NET comun și două interfețe independente, care îl pornesc și îl folosesc fiecare din procesul propriu: Cliq Desktop (Electron și React) și extensia pentru Visual Studio (WPF). Niciuna dintre cele două interfețe nu conține logica de scanare, generare sau rulare: ambele sunt clienți ai aceluiași backend, comunicând cu el prin HTTP local și, pentru fluxuri de lungă durată (progresul unei rulări, evidențierea live), prin Server-Sent Events.

\section{Straturile backend-ului}

Backend-ul este organizat pe patru proiecte, fiecare cu o singură responsabilitate:

\begin{tabularx}{\textwidth}{@{}p{3.6cm}Y@{}}
\toprule \textbf{Proiect} & \textbf{Responsabilitate} \\
\midrule
\File{Cliq.Domain} & Modele imutabile (\File{PageDefinition}, \File{TestCase}, \File{CliqSettings} și celelalte), fără nicio dependință externă. \\
\File{Cliq.Application} & Interfețe și excepții de domeniu (\File{ITestRunner}, \File{WorkspaceInUseException} etc.), fără implementare. \\
\File{Cliq.Infrastructure} & Implementările reale: scanare (Puppeteer), rulare și localizare (Selenium), generare de cod, persistența workspace-ului. \\
\File{Cliq.Api} & Endpoint-urile HTTP și SSE, singurul punct de intrare folosit de cele două interfețe. \\
\bottomrule
\end{tabularx}

\section{Un backend, două procese-gazdă}

La fiecare pornire, atât Desktop cât și extensia Visual Studio lansează propria instanță a backend-ului ca proces copil (sidecar-ul extensiei, respectiv serviciul local pornit de Electron), pe un port liber, cu un token valabil doar pentru sesiunea curentă. Nu există un server \Cliq{} permanent, partajat între toți utilizatorii unei mașini; fiecare sesiune de lucru pornește și oprește propriul backend.

Singurul lucru cu adevărat comun între cele două procese-gazdă este workspace-ul de pe disc (vezi capitolul „Workspace-ul Cliq"): același format JSON, protejat de același mecanism de exclusivitate, indiferent care dintre cele două îl deschide la un moment dat.

\section{Două unelte de automatizare a browserului}

Scanarea și rularea folosesc două biblioteci diferite, alese pentru ce fac mai bine fiecare. Puppeteer citește DOM-ul randat al unei pagini deja deschise, pentru descoperirea elementelor. Selenium WebDriver conduce un browser separat, vizibil, pentru rularea interactivă din \Cliq{} și pentru codul NUnit generat: același motor pe care îl va folosi și integrarea continuă, ca un test care trece în \Cliq{} să se comporte identic și în afara lui.

\chapter{Cerințe, instalare și pornire}

\section{Cliq Desktop}

Versiunea curentă se pornește din proiect și necesită Node.js 24 LTS, .NET SDK 10 și Google Chrome. Microsoft Edge este necesar doar dacă workspace-ul este configurat să ruleze cu Edge pe Windows.

În directorul \File{frontend}, instalați dependențele și porniți aplicația:

\begin{lstlisting}
npm ci
npm run dev
\end{lstlisting}

Electron pornește automat serviciul local Cliq API, alege un port liber și creează un token valabil doar pentru sesiunea curentă. Backend-ul nu se pornește separat.

\section{Extensia Visual Studio}

Extensia de previzualizare necesită Windows x64, Visual Studio 17.0 sau ulterior și Chrome ori Edge instalat. Pachetul VSIX conține runtime-ul .NET și Node necesar.

\begin{enumerate}
  \item Închideți toate instanțele Visual Studio.
  \item Deschideți fișierul \File{Cliq.VisualStudio.vsix}.
  \item Selectați instalarea Visual Studio și apăsați \UI{Install}.
  \item Acceptați avertismentul pentru extensia nesemnată, dacă apare.
  \item Verificați \UI{Extensions > Manage Extensions > Installed > Cliq for Visual Studio}.
\end{enumerate}

Comenzile se găsesc în \UI{Extensions > Cliq}. Pentru dezinstalare, închideți IDE-ul și eliminați extensia din Visual Studio Installer sau programați eliminarea din Manage Extensions.

\chapter{Workspace-ul Cliq}

\section{Obiectiv}

Cliq Desktop și extensia Visual Studio sunt două procese independente, care pot rula pe rând sau, teoretic, simultan pe același proiect. Amândouă trebuie să citească și să scrie aceleași fișiere (pagini, teste, setări), fără să se suprascrie una pe alta și fără ca un proces oprit brusc să lase workspace-ul într-o stare inconsistentă sau blocat permanent. Formatul comun de workspace și mecanismul de exclusivitate care îl protejează, descrise în acest capitol, rezolvă această problemă.

\section{Decizii de proiectare}

Cele două interfețe citesc și scriu exact același format JSON sub \File{.cliq/}, fără nicio conversie între ele. Această alegere este ce face posibilă predarea workspace-ului de la o interfață la alta (vezi capitolul „Predarea către Desktop") fără un pas separat de sincronizare: oricare dintre cele două deschide direct ce a lăsat cealaltă.

Exclusivitatea scrierii este garantată pe două niveluri. În interiorul aceluiași proces, un registru în memorie respinge imediat o a doua deschidere a aceluiași workspace, fără a atinge sistemul de fișiere. Între procese diferite, de exemplu Desktop și extensia Visual Studio rulând simultan, garanția vine dintr-un fișier de lock (\File{workspace.lock}) deschis exclusiv pentru scriere; un al doilea proces care încearcă să-l deschidă primește o eroare de sistem, transformată într-un mesaj care indică cine deține deja workspace-ul: tipul de host, procesul, momentul deschiderii.

Dacă procesul care deținea lock-ul s-a închis brusc, fără să elibereze fișierul, o deschidere ulterioară reușește automat: sistemul de fișiere nu mai are niciun handle activ asupra lui, așa că fișierul poate fi rescris cu noul proprietar, fără nicio intervenție manuală. Dacă totuși fișierul rămâne indisponibil dintr-un motiv neașteptat, iar proprietarul nu poate fi citit (lipsă sau cu conținut corupt), eroarea afișată nu inventează un proprietar; raportează explicit că nu se cunoaște cine deține workspace-ul, în loc să ghicească.

Fiecare entitate persistată (proiect, setări, pagini, teste) poartă un \File{schemaVersion}, ca formatul să poată evolua fără să rupă workspace-urile existente. Fișierele sunt împărțite explicit în cele destinate Git (proiect, setări, pagini, teste) și cele locale, excluse prin \File{.gitignore} (secrete, rulări, capturi, istoric), reflectând ce poate fi partajat în echipă și ce ține strict de mediul local.

\section{Impact}

\begin{itemize}
  \item Desktop și extensia Visual Studio pot alterna liber asupra aceluiași workspace, fără pas de sincronizare sau risc de suprascriere reciprocă.
  \item Un proces căzut brusc nu lasă workspace-ul blocat permanent: o redeschidere ulterioară recuperează automat lock-ul orfan.
  \item Un conflict de acces primește un mesaj util despre cine deține workspace-ul, nu o eroare generică de fișier ocupat.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{itemize}
  \item Un workspace este directorul rădăcină al proiectului testat. În Desktop, \UI{Open workspace} alege directorul; la prima deschidere Cliq creează \File{.cliq}, la următoarele încarcă proiectul, paginile și testele existente.
  \item În Visual Studio, workspace-ul este dedus din soluția sau folderul deschis. Dacă trebuie ales explicit: clic dreapta în Solution Explorer pe \UI{Use as Cliq Workspace} sau \UI{Bind Project and Open Cliq Workbench}, apoi \UI{Extensions > Cliq > Open Workbench}.
  \item Un singur proces poate scrie workspace-ul la un moment dat; o a doua încercare de deschidere e respinsă cu un mesaj despre cine îl deține deja.
\end{itemize}

\begin{lstlisting}
.cliq/
  project.json
  settings.json
  pages/<page-id>.json
  tests/<test-id>.json
  runs/scan-reviews/
  runs/diffs/
  secrets.local.json
  pending-custom-methods.json
Generated/
  PageObjects/

\end{lstlisting}

\warningbox{Nu schimbați manual identificatorii din JSON. Pașii referă paginile și elementele prin ID-uri stabile, nu prin textul locatorului.}

În Workbench, fila \UI{Project} conține numele, URL-ul de bază, browserul implicit, directoarele și namespace-urile generate. Valorile implicite sunt \File{Generated/PageObjects}, \File{Generated/Tests}, \File{Generated.PageObjects} și \File{Generated.Tests}. Modificați câmpurile, apoi apăsați \UI{Save project}; căile trebuie să fie relative și să rămână în workspace.

\chapter{Interfața Desktop}

Fereastra are trei zone. Bara laterală conține \UI{Tests}, \UI{Runs}, căutarea și crearea testelor. Zona centrală conține numele paginii, \UI{Scan}, \UI{Generate}, \UI{Run} și editorul. În dreapta se află browserul cu Back, Forward, Reload și bara de adresă.

Introduceți o adresă și apăsați Enter. Dacă protocolul lipsește, aplicația adaugă \File{https://}. Sunt acceptate doar HTTP și HTTPS. Permisiunile, descărcările și ferestrele native ale paginii sunt blocate în browserul încorporat.

Lista testelor poate fi filtrată după nume sau etichete. Fila Runs arată ultima rulare din sesiunea curentă. Erorile apar într-un banner care poate fi închis prin clic.

\chapter{Scanarea paginilor}

\section{Obiectiv}

La fiecare rescanare a unei pagini deja folosite în teste, elementele trebuie recunoscute ca fiind aceleași ca la scanarea anterioară, altfel orice pas care le referă s-ar rupe la o simplă rescanare. În plus, o pagină poate conține structuri repetitive (rânduri de tabel, carduri dintr-o listă) pe care scanarea obișnuită le tratează ca elemente separate, fără să semnaleze că ar fi mai potrivit un singur element dinamic, parametrizat. Acest capitol acoperă ambele mecanisme: recunoașterea elementelor la rescanare și sugerarea automată a elementelor dinamice.

\section{Decizii de proiectare}

Recunoașterea la rescanare compară elementele proaspăt scanate cu cele salvate anterior, pe niveluri ordonate de la cel mai fiabil la cel mai puțin fiabil, aceeași ordine ca la descoperire (testId, apoi xpath, apoi css). O pereche este acceptată doar dacă exact un element vechi și exact unul nou au aceeași cheie la acel nivel; o cheie ambiguă, cu mai multe elemente vechi sau noi identice, nu este ghicită, ci lăsată pentru nivelul următor. Un element care nu se potrivește la niciun nivel este raportat direct ca nou, iar vechiul lui corespondent ca lipsă; nu există niciun fallback pozițional sau aproximativ. O primă variantă a soluției folosea și \File{id}/\File{name} ca niveluri suplimentare de potrivire; au fost eliminate, pentru că aceste valori pot fi regenerate de framework fără să indice de fapt același element.

Sugestiile de elemente dinamice urmează aceeași filosofie. Scanarea grupează controalele care ocupă aceeași poziție relativă într-o structură repetitivă deja detectată; un grup devine sugestie doar de la trei instanțe în sus, ca să nu fie propuse elemente dinamice pentru simple coincidențe de structură. Fiecare grup are nevoie de o ancoră stabilă (un XPath pentru containerul rândurilor) ca să construiască șablonul parametrizat; dacă nicio ancoră stabilă nu poate fi găsită, grupul este abandonat în întregime, nu i se construiește un șablon aproximativ pe bază de cale absolută.

\section{Impact}

\begin{itemize}
  \item Pașii unui test rămân valabili peste rescanări repetate, cât timp elementul își păstrează un locator dintre cele urmărite, fără intervenție manuală.
  \item O ambiguitate la recunoaștere nu produce niciodată o potrivire greșită, tăcută; în cel mai rău caz, elementul apare ca nou sau lipsă și cere o decizie a utilizatorului.
  \item Structurile repetitive frecvente sunt semnalate proactiv ca elemente dinamice candidate, în loc să rămână elemente statice, plate, câte unul per instanță găsită la scanare.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{enumerate}
  \item Navigați la pagină și așteptați conținutul relevant; autentificați-vă manual, dacă e nevoie.
  \item Verificați \UI{Page object name} (Cliq propune un nume din URL), apoi apăsați \UI{Scan} și așteptați mesajul cu numărul de elemente.
\end{enumerate}

Scannerul citește DOM-ul randat și poate descoperi elemente create de React, Angular sau Vue; \File{id} este numai indiciu de denumire, niciodată locator direct. Pentru redenumirea unei pagini deja scanate, modificați \UI{Page object name} și apăsați Enter sau mutați focusul; noul nume de fișier C\# apare la generare.

La o rescanare, rezultatul conține:

\begin{itemize}
  \item \textbf{matched}: elementul a fost regăsit și își păstrează ID-ul;
  \item \textbf{new}: elementul nu exista anterior;
  \item \textbf{missing}: elementul vechi nu mai apare și rămâne marcat \UI{Not found on last scan}.
\end{itemize}

Desktop aplică reconcilierea și afișează un banner cu locatorii noi și lipsă; Cliq nu repară automat locatorii. Pentru aprobarea fiecărei schimbări înainte de aplicare, folosiți staged review din Visual Studio.

Dacă \UI{Capture a screenshot after scanning} este activă, apare \UI{Scan screenshot}. Când scannerul găsește cel puțin trei controale cu structură repetitivă, apare bannerul \UI{possible dynamic elements found}; extindeți-l, verificați numele, acțiunea, numărul de instanțe și XPath-ul, apoi apăsați \UI{Add}. Închiderea bannerului ignoră sugestiile fără să creeze elemente.

\chapter[Strategia de identificare]{Strategia de identificare a elementelor}

\section{Obiectiv}

La scanare, fiecare element trebuie asociat cu un locator stabil. Diferite atribute sunt disponibile în funcție de pagină (un atribut de test dedicat, un XPath structural sau un selector CSS structural), iar preferința pentru unul sau altul diferă de la proiect la proiect. Funcționalitatea descrisă în acest capitol lasă utilizatorul să configureze ce strategii sunt încercate și în ce ordine, în loc să impună una fixă.

\section{Decizii de proiectare}

Trei strategii sunt disponibile: \File{testId} (citește atributul configurat, implicit \File{data-testid}), \File{xpath} (construiește o cale structurală în DOM) și \File{css} (construiește un selector CSS structural). Prima strategie din ordinea configurată care produce un locator valid pentru element este cea folosită.

Selectorul CSS structural reușește pentru aproape orice element, fiind construit direct din poziția lui în DOM, nu dintr-un atribut care poate lipsi. Din acest motiv, inițial nu figura ca strategie propriu-zisă în listă, ci doar ca fallback necondiționat, aplicat tacit după ce toate celelalte strategii eșuau; utilizatorul nu îl putea nici plasa mai sus în ordine, dacă îl considera mai stabil decât un XPath lung, nici exclude complet.

Soluția adoptată promovează css la rangul celorlalte două strategii, ordonabilă explicit în \File{strategyOrder}. Fallback-ul necondiționat rămâne neschimbat pentru workspace-urile a căror ordine nu include css deloc: un element care epuizează toate strategiile listate primește oricum un locator, în loc să rămână fără niciunul.

\section{Impact}

\begin{itemize}
  \item css poate fi plasat oriunde în ordinea de căutare, inclusiv înaintea xpath sau testId, nu doar folosit tacit ca ultimă soluție.
  \item Comportamentul unui workspace existent, a cărui ordine nu menționează css, rămâne neschimbat: fallback-ul necondiționat continuă să garanteze un locator pentru orice element.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{itemize}
  \item \UI{Test ID attribute}: atributul citit de strategia \File{testId}; implicit \File{data-testid}.
  \item \UI{Strategy order}: poate conține \File{testId}, \File{xpath} și \File{css}, în orice ordine; prima care produce un locator valid câștigă. Se editează cu \UI{Move up}/\UI{Move down}, \UI{Remove} și \UI{Add strategy}; lista nu poate fi goală.
  \item \UI{Ignore ID patterns}: câte o expresie regulată pe linie, pentru identificatori generați automat (de framework-uri precum Ember, React Select, Angular, sau UUID-uri) care nu ar trebui folosiți ca nume sugerate. Valorile implicite acoperă aceste cazuri; expresiile introduse trebuie să fie valide.
\end{itemize}

Setările se salvează cu \UI{Save settings}; mesajul de validare explică orice eroare.

\chapter[Staged scan review]{Staged scan review în Visual Studio}

\section{Obiectiv}

O rescanare poate schimba structura unei pagini deja folosite în teste: apar elemente noi, altele dispar. Scrierea directă a acestor schimbări peste pagina existentă ar putea rupe teste care depind de un element eliminat, fără ca utilizatorul să observe la momentul scanării. Staged Scan Review introduce un pas de validare între scanare și scriere: rezultatul este comparat cu pagina activă, iar fiecare schimbare așteaptă o decizie explicită înainte de a fi aplicată.

\section{Decizii de proiectare}

Fiecare element modificat primește exact două acțiuni posibile, simetrice cu tipul schimbării: pentru un element nou, \UI{Add} sau \UI{Omit}; pentru un element lipsă, \UI{Remove} sau \UI{Keep}. Deciziile pot fi date individual, per element, sau în lot, pe trei niveluri de scop: pe categorie (toate elementele noi, respectiv toate cele lipsă) sau pe întregul review. Cele trei niveluri coexistă, fără ca vreunul să le înlocuiască pe celelalte: un review poate conține sute de elemente, iar utilizatorul are frecvent încredere doar într-o categorie de schimbări (de exemplu acceptă toate elementele noi, dar vrea să decidă individual asupra celor lipsă, care pot fi încă referite de teste existente).

În fereastră, acțiunile în lot sunt grupate într-un singur rând, ordonate de la cel mai restrâns scop la cel mai larg (categorie, apoi tot review-ul), deasupra listei derulabile de elemente. Nu sunt plasate lângă titlul fiecărei categorii din interiorul listei, unde ar ieși din câmpul vizual imediat ce utilizatorul derulează mai departe.

Aplicarea deciziilor este ținută separat de eliminarea elementelor referite de teste existente: o astfel de eliminare este blocată explicit, cu testul și pasul afișate, în loc să fie permisă tăcut și să lase un test cu o referință invalidă.

\section{Impact}

\begin{itemize}
  \item O schimbare de structură a paginii nu se propagă niciodată direct peste elementele existente; trece întotdeauna printr-o decizie vizibilă.
  \item Utilizatorul poate acționa la nivelul potrivit (un element, o categorie sau tot review-ul), fără să piardă controlul individual acolo unde are nevoie de el.
  \item Un test care ar rămâne fără elementul pe care îl referă este protejat: eliminarea acelui element este blocată, nu doar semnalată după fapt.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{enumerate}
  \item Se pornește din \UI{Scan Page...}, din \UI{Rescan} în Page inspector, sau din \UI{Scan URL in Cliq...} pentru un URL selectat; se completează URL-ul, numele, browserul și opțiunea headless, apoi \UI{Scan}. Operația poate fi anulată în timp ce rulează.
  \item Pagina activă nu este scrisă înainte de review. Fiecare element modificat cere o decizie:
  \begin{tabularx}{\textwidth}{@{}p{3.5cm}YY@{}}
  \toprule \textbf{Schimbare} & \textbf{Accept} & \textbf{Deny} \\
  \midrule
  Element nou & \UI{Add}: adaugă elementul. & \UI{Omit}: nu îl adaugă. \\
  Element lipsă & \UI{Remove}: elimină elementul. & \UI{Keep}: păstrează definiția veche. \\
  \bottomrule
  \end{tabularx}
  \item Deciziile se dau individual, sau în lot cu \UI{Accept New}/\UI{Deny New}, \UI{Accept Missing}/\UI{Deny Missing} ori \UI{Accept All}/\UI{Deny All}. O acțiune în lot suprascrie doar deciziile din categoria vizată.
  \item \UI{Apply} necesită o decizie pentru fiecare element din review. Eliminarea unui element referit de un test este blocată, iar testul și pasul care îl folosesc sunt afișate.
  \item Un review devenit vechi, cu pagina schimbată între timp, cere o rescanare. \UI{Discard} lasă pagina nemodificată.
\end{enumerate}

\chapter{Elemente dinamice}

\section{Obiectiv}

O scanare descoperă elemente fixe: fiecare este o instanță unică, prezentă o singură dată pe pagină la momentul scanării. Un tabel cu rânduri generate din date, unde utilizatorul vrea să acționeze pe rândul N sau pe rândul cu o anumită cheie, nu are o instanță fixă de descoperit: numărul și conținutul rândurilor depind de date, nu de structura paginii. Elementele dinamice acoperă acest caz: un locator definit manual, parametrizat, în loc de unul descoperit automat.

\section{Decizii de proiectare}

Un element dinamic este definit printr-un șablon de locator (XPath sau CSS) care conține tokenul literal \File{\{param\}}, plus tipul parametrului: \File{Index (int)} pentru poziție numerică, \File{Key (string)} pentru o cheie stabilă din date. La generare, șablonul devine o metodă parametrizată în loc de un câmp fix; apelantul furnizează valoarea la fiecare utilizare, nu la scanare.

Elementele dinamice devin membri ai aceleiași clase generate ca elementele statice ale paginii, așa că numele lor sunt validate împreună, nu separat: două elemente, dinamic și dinamic sau dinamic și static, care ar genera același nume de membru sunt respinse la salvare, nu lăsate să intre în coliziune tăcut, abia la compilarea codului generat. Din același motiv, șablonul este validat să conțină efectiv tokenul \File{\{param\}}, iar strategia locatorului este limitată la cele deja acceptate de generator; nu orice text arbitrar poate deveni șablon.

\section{Impact}

\begin{itemize}
  \item Elemente cu instanțe multiple, dependente de date (rânduri de tabel, liste generate), pot fi testate fără să fie descoperite individual la scanare.
  \item O coliziune de nume între un element dinamic și orice alt element al paginii este respinsă la salvare, nu descoperită abia la compilarea codului generat.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{enumerate}
  \item În Desktop, extindeți \UI{Dynamic elements}, selectați pagina și apăsați \UI{Add dynamic element}.
  \item Introduceți un nume unic și alegeți acțiunea: \UI{Click}, \UI{Fill}, \UI{Select} sau \UI{Assert text}.
  \item Alegeți strategia locatorului și introduceți un șablon care conține tokenul \File{\{param\}}, de exemplu:
\begin{lstlisting}
//table/tbody/tr[{param}]/td[2]/button
//tr[@data-key='{param}']//button
\end{lstlisting}
  \item Alegeți \UI{Index (int)} ori \UI{Key (string)} și apăsați \UI{Save}.
\end{enumerate}

Pentru utilizare într-un pas, selectați pagina, deschideți grupul \UI{Dynamic}, alegeți elementul și completați \UI{Parameter value}. Coșul din \UI{Dynamic elements} șterge definiția; verificați întâi pașii care o folosesc.

\chapter{Page inspector și întreținere}

\section{Obiectiv}

Pe măsură ce o pagină evoluează, elementele ei se pot demoda (marcate not found după o rescanare), iar pagina însăși poate avea nevoie să fie curățată, duplicată ca punct de plecare pentru una asemănătoare, sau ștearsă. Aceste operații de întreținere ating adesea teste existente, care referă pagina sau elementele ei; capitolul descrie cum sunt tratate consecințele fiecăreia.

\section{Decizii de proiectare}

Curățarea elementelor marcate not found (\UI{Remove not found elements}) este o operație în lot, fără verificare automată a referințelor din teste: responsabilitatea rămâne a utilizatorului, avertizat explicit să verifice întâi pașii care le folosesc. Alegerea contrastează deliberat cu Staged Scan Review, unde eliminarea unui element referit e blocată complet: aici utilizatorul lucrează direct pe pagina deja deschisă, cu control fin asupra fiecărui element, nu printr-un flux automat de reconciliere; avertismentul, nu blocarea, e tratamentul potrivit pentru o acțiune pe care oricum o inițiază manual.

Ștergerea unei pagini urmează un tratament diferit, dar tot fără blocare necondiționată: referințele din teste sunt calculate și afișate înainte de confirmare, ca utilizatorul să decidă în cunoștință de cauză, nu să fie oprit categoric. O pagină poate fi ștearsă intenționat chiar dacă un test încă o referă, dacă acel test urmează oricum să fie actualizat sau eliminat separat. Duplicarea unei pagini copiază integral definiția, toate elementele și elementele dinamice, sub un id nou, ca punct de plecare independent, fără nicio legătură ulterioară cu originalul.

\section{Impact}

\begin{itemize}
  \item Curățarea elementelor învechite nu cere o rescanare completă: se face direct în tabel, pe cele deja marcate not found.
  \item Ștergerea unei pagini nu e niciodată o surpriză: utilizatorul vede exact ce teste ar rămâne cu o referință ruptă, înainte să confirme.
  \item O pagină asemănătoare cu una existentă poate porni dintr-o copie completă, nu de la zero.
\end{itemize}

\section{Din perspectiva utilizatorului}

Selectați \UI{Pages}, apoi pagina și fila \UI{Page inspector}. Tabelul arată numele, tag-ul, acțiunea, locatorul și starea. Filtrarea caută după nume, tag sau locator. Meniul contextual copiază locatorul, iar dublu clic încearcă localizarea în browser.

\chapter{Localizarea în browser}

\section{Obiectiv}

Verificarea manuală a unui locator generat (mai există elementul pe pagină, exact acolo unde spune comentariul care îl documentează?) ar necesita altfel fie rularea unui test întreg, fie căutarea manuală a elementului în browser. Funcționalitatea descrisă în acest capitol localizează un singur element direct din codul generat, cu un comportament de tip inspector DevTools: se selectează comentariul locatorului, iar Cliq deschide sau reutilizează un browser și evidențiază elementul.

\section{Decizii de proiectare}

Fereastra de browser este ținută deschisă și reutilizată între apeluri succesive, o singură instanță per pagină, nu una nouă la fiecare localizare. Alegerea altui locator din același fișier reevidențiază în aceeași fereastră, nu deschide una nouă; sesiunea nu este niciodată închisă proactiv de Cliq, ci rămâne sub controlul utilizatorului cât timp acesta continuă să inspecteze pagina respectivă.

Un eșec la localizarea unui anumit element, atunci când locatorul nu se mai potrivește, nu invalidează sesiunea: fereastra rămâne deschisă, gata pentru o încercare cu alt locator. Doar un eșec la crearea sau navigarea sesiunii propriu-zise, când fereastra nu poate fi deschisă deloc, o închide și o elimină din pool, ca următoarea încercare să pornească de la zero.

Legătura dintre poziția din codul generat și elementul din pagină nu este memorată separat, ca o corespondență stocată: ar putea rămâne desincronizată de fișierul real la orice regenerare ulterioară. În schimb, textul comentariului selectat este comparat cu ce ar genera, chiar acum, fiecare element al paginii; elementul al cărui comentariu recalculat se potrivește exact este cel căutat. Un comentariu de element dinamic (șablon, fără o valoare de parametru) este respins explicit; nu are o singură instanță de localizat.

\section{Impact}

\begin{itemize}
  \item Verificarea unui locator nu cere pornirea unui test întreg, nici căutarea manuală a elementului în browser.
  \item Localizări repetate pe aceeași pagină rămân rapide: o singură fereastră de browser, nu una nouă de fiecare dată.
  \item Legătura comentariu-element rămâne mereu corectă față de fișierul curent, pentru că se recalculează la fiecare cerere, nu se citește dintr-un index care ar putea fi desincronizat.
\end{itemize}

\section{Din perspectiva utilizatorului}

Pentru \UI{Locate in Browser}, deschideți Page Object-ul, poziționați cursorul pe locator sau pe comentariul lui și folosiți meniul contextual. Cliq deschide ori reutilizează browserul și evidențiază elementul. Comentariile elementelor dinamice (șabloane) nu pot fi localizate direct din sursă; le lipsește o valoare de parametru.

\chapter[Evidențierea live a elementelor]{Evidențierea live a elementelor în Page inspector}

\section{Obiectiv}

Localizarea unui element cunoscut de \Cliq{} în Page inspector se făcea, până la această funcționalitate, printr-o acțiune punctuală: utilizatorul alegea un element din tabel, iar \Cliq{} îl evidenția o singură dată în browser. Nu exista și sensul invers, de la un element vizibil în browser către rândul lui din tabel, util mai ales pe pagini cu multe elemente asemănătoare, greu de distins doar după nume. Funcționalitatea descrisă în acest capitol adaugă acest sens invers, sub forma unei evidențieri live a elementului aflat sub cursor.

\section{Decizii de proiectare}

Fluxul de rulare a testelor expune deja un canal de tip Server-Sent Events pentru progresul unei rulări. Evidențierea live reutilizează același mecanism de transport, în loc să introducă unul nou (interogare periodică sau WebSocket): browserul rămâne cel deschis de Selenium, iar backend-ul instalează un tracker de hover în pagină care urmărește continuu poziția cursorului. Un eveniment este trimis doar în momentul în care elementul cunoscut aflat sub cursor se schimbă (de la un element la altul, sau de la un element la niciunul), nu la fiecare mișcare a mouse-ului cât timp cursorul rămâne pe același element.

Spre deosebire de fluxul de rulare, acest stream nu are un eveniment final de tip „done": rulează până când utilizatorul dezactivează evidențierea live sau conexiunea se întrerupe dintr-un alt motiv. Cele două cazuri sunt distinse explicit (oprire cerută de utilizator, față de o deconectare neașteptată), astfel încât apelantul poate reacționa diferit la fiecare.

Pe partea de extensie, starea evidențierii live este urmărită separat de restul acțiunilor (scanare, generare, rulare), care ocupă pe rând un singur loc de operație activă. Motivul: o evidențiere live rulează pe o durată nedeterminată, iar o scanare sau o generare pornită cât timp evidențierea e activă trebuie să funcționeze neschimbat, nu blocată de un stream care oricum nu s-a încheiat.

\section{Impact}

\begin{itemize}
  \item Page inspector capătă un sens de căutare invers: de la elementul vizibil în browser către rândul lui din tabel, util pe pagini cu multe elemente similare.
  \item Mecanismul de transport (parsarea liniilor stream-ului) este partajat cu fluxul de progres al rulărilor, în loc să fie duplicat: o singură implementare de întreținut pentru protocolul de stream.
  \item Evidențierea live nu blochează celelalte acțiuni ale workspace-ului: o scanare sau o generare pot porni normal cât timp evidențierea rulează.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{enumerate}
  \item În Visual Studio, se deschide \UI{Page inspector} pentru pagina dorită.
  \item Se apasă butonul \UI{Start Live Highlight}.
  \item Cât timp evidențierea este activă, mutarea cursorului peste un element cunoscut în browserul de test evidențiază automat rândul corespunzător din tabel.
  \item Se apasă din nou butonul pentru oprire.
\end{enumerate}

\chapter{Crearea și editarea testelor}

\section{Obiectiv}

Un pas de test descrie o intenție funcțională (completează acest câmp, apasă acest buton, bifează această opțiune) fără ca autorul să scrie cod. Editorul de pași, comun ambelor interfețe, transformă această intenție într-o listă ordonată de acțiuni, fiecare legată de o pagină și un element deja scanate.

\section{Decizii de proiectare}

Setarea unui checkbox nu apasă necondiționat elementul, ci compară starea curentă cu starea cerută și apasă doar dacă diferă. Alegerea contează pentru că un checkbox HTML nu are o operație de „setare" nativă, doar comută la fiecare click, așa că o apăsare necondiționată ar putea inversa exact starea dorită, dacă elementul se întâmplă să fie deja corect (de exemplu la o rulare repetată, pe o pagină a cărei stare nu se resetează de la o sesiune la alta). Aceeași verificare este emisă identic, indiferent dacă pagina generată e autonomă sau moștenește dintr-un \File{BasePage} comun.

Assert URL este singura acțiune care nu cere nici pagină, nici element: compară direct URL-ul curent cu o expresie regulată, ceea ce îi permite să verifice o navigare produsă de altă acțiune (de exemplu un submit de formular), fără să depindă de un element anume de pe pagina de destinație.

\section{Impact}

\begin{itemize}
  \item Un test poate rula repetat, pe o pagină a cărei stare de checkbox nu e resetată de fiecare dată, fără riscul de a inversa accidental o stare deja corectă.
  \item Verificarea unei navigări nu necesită un element ancoră pe pagina de destinație, doar tiparul URL-ului.
\end{itemize}

\section{Test nou în Desktop}

\chapter{Gestionarea secretelor}

\section{Obiectiv}

Un test conține adesea date sensibile (o parolă, un token) necesare pentru a completa un formular sau a autentifica un utilizator de test. Salvarea directă a acestor valori în fișierul testului le-ar expune oriunde ajunge fișierul, inclusiv într-un istoric Git. Mecanismul descris în acest capitol separă cheia, care poate fi văzută și versionată, de valoare, care nu părăsește niciodată mediul local sau de execuție.

\section{Decizii de proiectare}

O valoare de pas poate fi \UI{Literal} (salvată direct în testul JSON) sau \UI{Secret} (salvează doar o cheie simbolică, de exemplu \File{login.password}). Valoarea propriu-zisă a unui secret există doar în două locuri, niciodată amândouă în același fișier versionat: local, în \File{.cliq/secrets.local.json} (exclus explicit prin \File{.gitignore}), folosit când testul rulează interactiv din Cliq; și în mediul de execuție, ca variabilă de sistem, când testul generat rulează independent, prin \File{dotnet test}.

Codul NUnit generat citește secretul direct din variabila de mediu la momentul rulării, cu numele derivat mecanic din cheie (\File{login.password} devine \File{CLIQ\_LOGIN\_PASSWORD}), și eșuează explicit, cu un mesaj clar, dacă variabila lipsește, în loc să continue cu o valoare goală. Nicio etapă a fluxului, nici fișierul testului, nici codul generat, nu conține vreodată valoarea propriu-zisă; doar cheia și, separat, mecanismul de citire.

\section{Impact}

\begin{itemize}
  \item Fișierul unui test poate fi comis în Git în siguranță, indiferent câte valori Secret conține: doar cheile sunt persistate acolo.
  \item Rularea codului generat în afara Cliq (integrare continuă, linia de comandă) necesită doar setarea variabilelor de mediu corespunzătoare cheilor folosite.
  \item O cheie fără valoare configurată local nu trece neobservată: rularea interactivă din Cliq și \File{dotnet test} eșuează amândouă explicit, nu cu o valoare goală.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{itemize}
  \item În fila \UI{Secrets} din Visual Studio, \UI{+ Add secret} introduce cheia și valoarea. Cheia începe cu literă sau underscore și poate conține litere, cifre, punct, minus și underscore; valoarea nu poate fi goală. Interfața afișează o mască, nu valoarea; \UI{Update value} o înlocuiește, \UI{Delete} o elimină.
  \item La un pas, o valoare \UI{Secret} referă cheia definită în Secrets, nu introduce direct o valoare.
\end{itemize}

\warningbox{Nu salvați parole ca Literal. Fișierul testului poate fi comis în Git.}

Pentru rularea codului generat în afara Cliq, definiți variabilele de mediu corespunzătoare. Exemplu PowerShell:

\begin{lstlisting}
$env:CLIQ_LOGIN_PASSWORD = "valoarea-din-mediul-de-test"
dotnet test
\end{lstlisting}

\chapter{Rularea testelor}

\section{Obiectiv}

Un test trebuie să poată fi urmărit vizual în timp ce rulează, ca să se vadă exact ce element e vizat înainte de fiecare acțiune, iar un eșec să poată fi diagnosticat imediat, nu doar dedus dintr-un mesaj de eroare. Rularea interactivă din Cliq oferă exact asta, folosind același motor Selenium ca testul NUnit generat, astfel încât un test care trece în Cliq să se comporte identic și în afara lui.

\section{Decizii de proiectare}

Fereastra de browser este întotdeauna vizibilă, niciodată headless: o alegere fixă, nu o opțiune de configurare, pentru că întregul scop al rulării interactive este observarea ei. Înainte de fiecare acțiune, elementul țintă este localizat, evidențiat, urmează o pauză configurabilă, apoi este relocalizat și abia atunci acționat; relocalizarea de după pauză există ca acțiunea să opereze pe o referință proaspătă, nu pe una posibil învechită de orice ar fi putut mișca pagina în timpul pauzei vizuale.

Durata fiecărui pas este împărțită explicit în timp de localizare și timp de acțiune, nu raportată ca un singur total: distincția arată dacă un pas lent așteaptă apariția elementului sau dacă acțiunea propriu-zisă durează, două cauze diferite de diagnosticat. La eșec, dacă opțiunea e activă, este capturat un screenshot cu elementul localizat evidențiat, aceeași infrastructură de evidențiere folosită de localizarea din browser și de evidențierea live.

\section{Impact}

\begin{itemize}
  \item Un eșec poate fi diagnosticat vizual, imediat, fără o rulare separată doar pentru depanare.
  \item Un test care trece în Cliq folosește exact motorul pe care îl va folosi și codul NUnit generat: nicio diferență de comportament între cele două.
  \item Timpul de localizare separat de timpul de acțiune indică direct unde se duce timpul unui pas lent.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{enumerate}
  \item Selectați un test cu cel puțin un pas activ.
  \item Apăsați \UI{Run} în Desktop sau \UI{Run test} în Workbench.
  \item Cliq deschide o fereastră Selenium vizibilă.
  \item Urmăriți starea, durata, timpul de localizare și timpul acțiunii.
\end{enumerate}

În Visual Studio se poate alege Chrome sau Edge în fereastra Run Results. Testul poate fi pornit și din fișierul JSON prin \UI{Run Cliq Test}. \UI{Cancel run} oprește execuția și închide browserul.

\chapter{Generarea codului}

\section{Obiectiv}

Un pas de test descrie o acțiune la nivel funcțional (completează, selectează, verifică) fără cod. Generarea de cod transformă paginile și testele definite în Cliq într-o clasă Page Object per pagină și o clasă de test NUnit per test, astfel încât fluxul de autor din Cliq să se încheie cu cod C\# obișnuit, care poate fi citit, rulat și versionat independent de Cliq.

\section{Decizii de proiectare}

Fiecare element cu locator fix, toate mai puțin Radio, a cărui țintă depinde de opțiunea aleasă la runtime, devine un câmp static, calculat o singură dată la nivel de clasă, nu reconstruit de fiecare dată când o metodă îl folosește.

Elementele Fill și Select au, spre deosebire de Click sau Assert, atât o acțiune de scriere cât și una de citire a valorii curente. În loc de două metode separate per element, fiecare astfel de element devine o proprietate de tip \File{ElementWrapper<TData>}: o singură clasă generată o dată per namespace, nu per pagină, care perechează un locator cu acces tipizat de citire și scriere. Tipul concret variază după natura datelor (\File{string}, \File{int} sau \File{DateTime} pentru Fill, în funcție de input; un șir de valori pentru multi-select), dar forma API-ului, \File{Upload}/\File{Read}, rămâne aceeași pentru orice element de acest fel.

\section{Impact}

\begin{itemize}
  \item Un locator fix este calculat o singură dată per clasă, nu reconstruit la fiecare apel al metodei care îl folosește.
  \item Elementele cu scriere și citire au un API uniform, tipizat, indiferent de tipul datelor pe care îl poartă.
  \item Fluxul se încheie cu cod C\# obișnuit: citit, rulat și versionat ca orice alt fișier din proiect, fără dependență de Cliq la execuție.
\end{itemize}

\section{Din perspectiva utilizatorului}

În Desktop, selectați testul și apăsați \UI{Generate}. Sunt incluse testul, paginile referite și pagina curentă, chiar dacă nu este încă folosită de un pas. Fără test selectat se poate genera workspace-ul complet.

\chapter[Generarea clasei de bază BasePage]{Generarea clasei de bază (\File{BasePage}) după stilul unui Page Object existent}

\section{Obiectiv}

Un proiect care folosește deja Selenium poate avea o convenție proprie pentru clasa de bază a Page Object-urilor: numele câmpului pentru driver, numele câmpului de tip \File{WebDriverWait} sau alte convenții de denumire. Fără o modalitate de a prelua această convenție, codul generat de \Cliq{} ar introduce un al doilea stil, paralel cu cel existent, în același proiect. Funcționalitatea descrisă în acest capitol generează o clasă de bază comună, \File{BasePage.cs}, ai cărei membri sunt derivați parțial dintr-un Page Object exemplu indicat de utilizator; paginile generate ulterior moștenesc din ea.

\section{Decizii de proiectare}

O primă variantă a soluției presupunea moștenirea directă din clasa de bază deja existentă în proiect. Abordarea a fost abandonată: comportamentul acelei clase nu este controlat de \Cliq{}, iar orice modificare structurală a ei (semnătura constructorului, redenumirea unui membru) putea rupe compilarea codului generat, fără ca eroarea să provină din \Cliq{} însuși.

Soluția adoptată inversează relația: \Cliq{} generează propria clasă \File{BasePage}, iar din exemplul indicat preia \emph{doar convenția de denumire}: numele parametrului și al câmpului pentru driver, respectiv numele câmpului \File{WebDriverWait}, dacă acesta există. Alegerile structurale, ce metode conține \File{BasePage}, cum este tratat un click interceptat de un element tranzitoriu, nu sunt preluate din exemplu, ci aparțin exclusiv logicii de generare a \Cliq{}.

Extragerea stilului din exemplu este realizată prin analiză sintactică Roslyn, fără compilare, aceeași abordare folosită și la verificarea metodelor personalizate. Alegerea elimină dependența de compilarea proiectului sursă al exemplului; este suficient ca fișierul să fie sintactic valid.

\section{Impact}

\begin{itemize}
  \item Codul generat nu mai depinde, la compilare sau la execuție, de o clasă externă neîntreținută de \Cliq{}.
  \item Logica de interacțiune tolerantă la suprapuneri tranzitorii (un tooltip sau un banner care blochează temporar un click) este centralizată o singură dată în \File{BasePage}, în loc să fie duplicată în fiecare pagină generată.
  \item Un proiect cu o convenție de denumire deja stabilită poate adopta codul generat de \Cliq{} fără o rescriere a claselor existente.
  \item Membrii din \File{BasePage} sunt declarați \File{virtual}; o pagină individuală îi poate suprascrie printr-o metodă marcată \File{[CliqCustomMethod]}, păstrată la regenerare.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{enumerate}
  \item În \UI{Cliq settings > Base page matching} se introduce calea relativă către un Page Object \File{.cs} existent în workspace.
  \item La generare, \Cliq{} citește convențiile de denumire din fișierul indicat și creează \File{BasePage.cs} în directorul de ieșire configurat.
  \item Paginile generate ulterior moștenesc din \File{BasePage} și folosesc câmpurile acesteia în locul propriilor câmpuri de driver și wait.
  \item Câmpul rămâne gol pentru generarea unor clase autonome, fără clasă de bază comună; comportamentul implicit, nemodificat.
\end{enumerate}

\chapter{Metode custom și Pending Merges}

\section{Obiectiv}

O clasă Page Object este regenerată integral de fiecare dată, pornind din elementele scanate. O metodă scrisă manual în același fișier, de exemplu una care combină mai mulți pași într-o singură acțiune, ar fi ștearsă la următoarea generare, fără o cale explicită de a o păstra. Funcționalitatea descrisă în acest capitol permite unei metode marcate să supraviețuiască regenerării, iar orice ambiguitate despre ce se întâmplă cu ea este tratată printr-o decizie a utilizatorului, nu printr-o presupunere automată.

\section{Decizii de proiectare}

O metodă supraviețuiește doar dacă poartă atributul \File{[CliqCustomMethod]}; orice altceva din fișier este înlocuit necondiționat la regenerare. Extragerea metodelor marcate folosește analiză sintactică Roslyn, nu doar numărarea acoladelor, ca să fie detectate și metodele cu erori reale de sintaxă, nu doar cele nepotrivite ca formă.

Prima variantă a soluției recupera automat metodele marcate și afișa doar un avertisment pasiv când extragerea eșua parțial. Abordarea a fost înlocuită cu o alegere activă: fiecare metodă marcată este prezentată individual, iar utilizatorul decide explicit ce se întâmplă cu ea: \UI{Carry over} pentru păstrare, \UI{Defer} pentru amânare într-o listă de așteptare, sau \UI{Discard permanently} pentru eliminare definitivă. Nu există o decizie implicită aplicată tacit.

O rafinare ulterioară a extins regula la orice pagină cu cel puțin o metodă custom, nu doar la cele cu o recuperare eșuată: chiar și metodele care s-ar recupera perfect cer, la fiecare regenerare, o confirmare explicită. Motivul este consecvent cu restul aplicației: nicio corecție silențioasă, nicio presupunere aplicată tacit, extins acum și la codul scris manual; chiar dacă recuperarea automată ar reuși de fiecare dată, lipsa unei confirmări explicite ar însemna, în fond, o presupunere tacită.

Regula are un cost asumat: regenerarea întregii pagini este blocată cât timp există o metodă custom nerezolvată, nu doar partea care o privește. Un element nou-scanat pe acea pagină nu ajunge în fișierul generat până la rezolvare. Fișierul rămâne complet neatins până la decizie, în ambele situații care o cer: o redenumire de pagină cu metode custom în fișierul vechi, sau o regenerare cu același nume.

Interfața Electron (Cliq Desktop) nu a fost extinsă cu acest flux: vede în continuare doar avertismentul pasiv original, fără fereastra de merge. O pagină cu metode custom nu mai produce niciun artefact nici pentru Desktop, fără nicio explicație vizibilă acolo; rămâne un decalaj cunoscut, neînchis încă.

\section{Impact}

\begin{itemize}
  \item Nicio metodă scrisă manual nu poate fi pierdută sau suprascrisă fără o decizie explicită a utilizatorului.
  \item Regenerarea unei pagini cu metode custom nerezolvate este blocată integral, nu parțial; cost asumat pentru garanția de mai sus.
  \item Lista de așteptare este unică pe tot workspace-ul, nu per pagină, dar fiecare intrare rămâne asociată paginii de origine.
  \item Interfața Desktop rămâne, deocamdată, fără acces la acest flux: o pagină cu metode custom e stabilă acolo doar dacă rămâne nemodificată.
\end{itemize}

\section{Din perspectiva utilizatorului}

O metodă manuală supraviețuiește regenerării numai marcată cu \File{[CliqCustomMethod]}:

\begin{lstlisting}[language={[Sharp]C}]
[CliqCustomMethod]
public void ConfirmOrder()
{
    _driver.FindElement(ConfirmButtonLocator).Click();
}
\end{lstlisting}

Fereastra \UI{Pending Merges} se deschide automat la orice regenerare a unei pagini cu cel puțin o metodă custom, indiferent dacă recuperarea ar reuși curat sau nu, sau manual, din comanda \UI{Pending Merges}.

În \UI{Pending Merges > Resolve conflicts}:

\begin{enumerate}
  \item Extindeți metoda și citiți sursa.
  \item Alegeți \UI{Carry over} pentru includere, \UI{Defer} pentru amânare ori \UI{Discard permanently} pentru eliminare.
  \item Apăsați \UI{Resolve}.
\end{enumerate}

Metodele cu sintaxă invalidă nu pot fi incluse; corectați fișierul și regenerați. În \UI{Waiting list}, \UI{Include now} include o metodă amânată, \UI{Discard} o elimină, iar Refresh recitește lista.

\warningbox{Discard permanently nu poate fi anulat din Cliq. Verificați sursa și istoricul Git înainte de alegere.}

\chapter{Predarea către Desktop}

\section{Obiectiv}

Desktop și extensia Visual Studio nu pot deține simultan rezervarea de scriere a aceluiași workspace (vezi capitolul „Workspace-ul Cliq"), dar utilizatorul are nevoie să treacă de la una la alta fără pași manuali, fără să elibereze și să redeschidă workspace-ul singur. Predarea automatizează exact această tranziție: extensia își eliberează propria rezervare, pornește Desktop și așteaptă, apoi recuperează rezervarea când Desktop se închide.

\section{Decizii de proiectare}

Cele două procese nu comunică direct între ele: nu există niciun canal prin care Desktop să anunțe extensia că a pornit sau că s-a închis. Extensia detectează indirect prezența lui Desktop prin comportamentul rezervării: după ce își eliberează propria rezervare și pornește Desktop, încearcă periodic să o recupereze. Cât timp încercarea eșuează, Desktop o deține încă; când reușește pentru prima dată, poate însemna fie că Desktop nu a apucat încă să o preia, fie că a preluat-o și a eliberat-o deja.

Pentru a distinge cele două cazuri, extensia ține minte dacă a observat vreodată rezervarea deținută de Desktop. Dacă da, o recuperare reușită ulterioară înseamnă că Desktop a terminat: predarea se încheie. Dacă nu, recuperarea reușită e doar o fereastră de timp în care Desktop încă nu a pornit sau nu a apucat să acționeze; extensia eliberează din nou rezervarea și continuă să aștepte, până la un timeout, dincolo de care presupune că Desktop nu a pornit corect și raportează eroarea, în loc să aștepte indefinit.

Dacă pornirea propriu-zisă a lui Desktop eșuează (executabilul lipsește, procesul nu poate fi lansat), extensia recuperează imediat propria rezervare: workspace-ul nu rămâne niciun moment fără proprietar din cauza unei predări eșuate. O a doua predare nu poate fi pornită cât timp una este activă, ca să nu existe două încercări concurente de aceeași parte.

\section{Impact}

\begin{itemize}
  \item Tranziția între cele două interfețe nu cere niciun pas manual de eliberare sau recuperare a workspace-ului.
  \item O predare eșuată (Desktop nu pornește) nu lasă workspace-ul blocat: extensia recuperează imediat rezervarea.
  \item O predare care depășește timpul de așteptare este raportată explicit, nu lăsată să aștepte la nesfârșit.
\end{itemize}

\section{Din perspectiva utilizatorului}

\begin{enumerate}
  \item Salvați modificările din Workbench.
  \item Alegeți \UI{Record in Cliq Desktop}.
  \item Extensia eliberează workspace-ul și pornește Desktop.
  \item Lucrați în Desktop, apoi închideți aplicația.
  \item Visual Studio recuperează rezervarea și reîncarcă datele.
\end{enumerate}

Dacă executabilul nu este găsit, configurați calea în \UI{Tools > Options > Cliq > General}. Nu poate fi pornită o a doua predare cât timp prima este activă.

\chapter{Depanare}

\section{Workspace sau scanare}

Dacă workspace-ul nu se deschide, verificați drepturile și JSON-ul din \File{.cliq}. O eroare schema version indică o versiune incompatibilă. Pentru scanare, verificați URL-ul HTTP/HTTPS și browserul instalat. Măriți Load timeout sau Network idle grace pentru pagini lente și încercați fără headless dacă site-ul se comportă diferit.

\section{Element ori test eșuat}

Verificați not found în Page inspector, folosiți Locate in Browser și rescanați. Cliq nu substituie locatorul automat. Testul trebuie să aibă un pas activ, ținte și valori complete. Secretul trebuie să existe local, iar pentru codul generat variabila \File{CLIQ_*} trebuie definită.

\section{Captură, generare și Desktop}

Activați opțiunea de captură înainte de operație; fișierele vechi pot fi curățate. Pentru avertismente de metode custom, nu ștergeți fișierul: folosiți Pending Merges. Dacă extensia nu găsește Desktop, configurați calea către \File{Cliq.exe} și verificați să nu existe alt proces care deține workspace-ul.

\chapter{Limitări și bune practici}

Extensia este o previzualizare nesemnată pentru Windows x64 și necesită un browser instalat. Desktop administrează elementele dinamice; extensia doar afișează sugestiile. Setările, secretele și ștergerea testelor sunt expuse complet în Visual Studio, nu în Desktop. Cliq nu înregistrează automat clicurile și textul introdus în browser: pașii se compun manual din elementele scanate. Comanda istorică \UI{Record in Cliq Desktop} face doar predarea workspace-ului către aplicația Desktop.

Folosiți atribute de test stabile, conturi dedicate, Git pentru definiții și review pentru fiecare generare. Nu comiteți secrete ori capturi. Nu editați conținutul generat decât în metode marcate. Folosiți staged review înainte de eliminări și testați cu același browser și aceleași variabile ca în CI.
